# Day 004: Script Execute Permissions

## 🎯 What I Did Today

Day 4 of my #100DaysOfDevOps challenge. Today's task was about file permissions — a backup
script had been dropped onto a server but couldn't actually run because it didn't have
execute permissions.

**The scenario**: a script `/tmp/xfusioncorp.sh` exists on the server but isn't executable.
Need to fix that, and make sure every user on the system can run it.

## Steps I Followed

1. SSH'd into the server the same way as previous days.

2. Checked the current permissions first, instead of just assuming:

    ```sh
    ls -la /tmp
    ```

    The script had no permissions at all set (`----------`) — nobody could read, write, or
    execute it.

3. Fixed it:

    ```sh
    sudo chmod 755 /tmp/xfusioncorp.sh
    ```

4. Verified the change actually applied:

    ```sh
    ls -la /tmp
    ```

    Now showing `-rwxr-xr-x` — owner has full rwx, group and others can read + execute.


## What I Took Away From This

- Never assume a permission problem — check with `ls -la` before and after
- `755` is the standard pattern for anything that needs to be executable by everyone but
  only writable by the owner
- The execute bit isn't just "run this program" — for directories it also controls whether
  you can access what's inside them

## Notes to Self

| Permission | Meaning | Octal Value |
|---|---|---|
| Read (r) | View file contents | 4 |
| Write (w) | Modify the file | 2 |
| Execute (x) | Run the file as a program | 1 |

| Common Pattern | Meaning | Use Case |
|---|---|---|
| `755` | rwxr-xr-x | Standard executable script |
| `644` | rw-r--r-- | Standard non-executable file |
| `600` | rw------- | Private file, owner only |
| `777` | rwxrwxrwx | Full access for everyone — avoid, it's a security risk |
