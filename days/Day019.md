# Day 019: Install and Configure Web Application

## 🎯 What I Did Today

Today's task was hosting two separate static websites behind a single Apache port,
each reachable at its own sub-path.

**The scenario**: install `httpd` on App Server 3, configure Apache to serve on port
`6300`, and set up two website backups (`beta` and `cluster`, sitting on the jump host)
so `beta` is reachable at `http://localhost:6300/beta/` and `cluster` at
`http://localhost:6300/cluster/`.


## Steps I Followed

1. Connected to App Server 3.

2. Installed Apache:

    ```sh
    sudo yum install httpd -y
    ```

3. Changed the listening port from `80` to `6300`:

    ```sh
    sudo grep -n "Listen" /etc/httpd/conf/httpd.conf
    sudo sed -i 's/^Listen 80/Listen 6300/' /etc/httpd/conf/httpd.conf
    ```

4. Copied both website folders from the jump host to App Server 3:

    ```sh
    scp -r /home/thor/beta user@stapp03:/tmp/
    scp -r /home/thor/cluster user@stapp03:/tmp/
    ```

5. Moved them into Apache's document root:

    ```sh
    sudo mv /tmp/beta /var/www/html/
    sudo mv /tmp/cluster /var/www/html/
    ```

   Since both folders are just subdirectories under the document root, no extra Apache
   config (like an `Alias`) was needed — anything under `/var/www/html/<folder>` is
   automatically reachable at `/<folder>/` by Apache's default behavior.

6. Fixed ownership and permissions so Apache could actually serve the files:

    ```sh
    sudo chown -R apache:apache /var/www/html/beta
    sudo chown -R apache:apache /var/www/html/cluster
    sudo chmod -R 755 /var/www/html/beta
    sudo chmod -R 755 /var/www/html/cluster
    ```

7. Also handled SELinux, since it can silently block Apache from serving files even when
   the regular Linux permissions look correct:

    ```sh
    sudo restorecon -Rv /var/www/html/beta
    sudo restorecon -Rv /var/www/html/cluster
    ```

8. Validated the config before restarting:

    ```sh
    sudo apachectl configtest
    ```

9. Started/restarted and enabled Apache:

    ```sh
    sudo systemctl restart httpd
    sudo systemctl enable httpd
    sudo systemctl status httpd
    ```

10. Opened the port on the firewall:

    ```sh
    sudo firewall-cmd --permanent --add-port=6300/tcp
    sudo firewall-cmd --reload
    ```

11. Tested both sites:

    ```sh
    curl http://localhost:6300/beta/
    curl http://localhost:6300/cluster/
    ```

## What I Took Away From This

- Hosting multiple sites under one Apache instance doesn't always need virtual hosts or
  aliases — if the content is just placed as subdirectories under the document root, the
  URL structure follows the folder structure automatically
- SELinux is a separate layer from regular file permissions — `chmod`/`chown` being correct
  doesn't guarantee Apache can serve the files if SELinux's file context is still wrong.
  `restorecon` fixes the context to match what's expected for that location
- Testing config with `apachectl configtest` before restarting is a habit worth keeping
  every time config gets edited, not just for SSL setups like Day 15
- A missing `index.html` inside a folder is an easy thing to overlook — worth checking the
  folder actually has one before assuming a blank/error response means something else is
  wrong

## Notes to Self

| Concept | Detail |
|---|---|
| Serving subdirectories | Files under `document_root/<folder>` are reachable at `/<folder>/` with no extra config |
| Document root | `/var/www/html/` by default on this setup |
| SELinux context fix | `restorecon -Rv <path>` — reapplies the expected security context |
| Config validation | `apachectl configtest` — check before restart, not after |

| Permission Setting | Purpose |
|---|---|
| `chown -R apache:apache <path>` | Apache needs ownership to read the files reliably |
| `chmod -R 755 <path>` | Standard readable/executable permissions for web content |
