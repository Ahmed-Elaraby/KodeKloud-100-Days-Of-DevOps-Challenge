# Day 013: IPtables Installation and Configuration

## 🎯 What I Did Today
Today's task was a security hardening one — Apache's port was open to the entire world 
with no firewall in front of it, and the fix needed to restrict it to only the load balancer, 
not just anyone who could reach the port.

**The scenario**: Apache's port `8089` is wide open on every app host with no firewall
installed. Requirements: install `iptables` on each app host, block incoming access to port
`8089` for everyone except the LBR (load balancer) host, and make sure the rules survive a
reboot.

## Why This Setup Makes Sense

In this kind of architecture, real traffic isn't supposed to hit each app server directly —
it goes through the load balancer, which then distributes it to the app servers behind it.
So there's no legitimate reason for anyone *except* the LBR to talk to Apache's port
directly. Locking that down doesn't break anything real, it just closes an unnecessary
exposure.

## Steps I Followed (repeated on each app host)

1. Installed `iptables` and its dependencies:

    ```sh
    sudo yum install iptables iptables-services -y
    ```

2. Made sure the service is running now and stays enabled across reboots:

    ```sh
    sudo systemctl start iptables
    sudo systemctl enable iptables
    ```

3. Got the LBR host's IP, since the allow rule needs a specific address, not a wildcard:

    ```sh
    cat /etc/hosts | grep -i lbr
    ```

4. Added a rule allowing only the LBR IP through on port `8089`:

    ```sh
    sudo iptables -I INPUT -p tcp -s <LBR_IP> --dport 8089 -j ACCEPT
    ```

5. Added a rule rejecting everyone else on that same port — and the **order matters** here,
   this rule has to come *after* the LBR allow rule, since iptables processes rules
   top-to-bottom and stops at the first match:

    ```sh
    sudo iptables -A INPUT -p tcp --dport 8089 -j REJECT
    ```

6. Double-checked the rule order before trusting it:

    ```sh
    sudo iptables -L INPUT -n -v --line-numbers
    ```

   Confirmed the LBR `ACCEPT` rule had a lower line number than the `REJECT` rule.

7. Saved the rules so they'd survive a reboot:

    ```sh
    sudo service iptables save
    ```

   (or, if that command isn't available: `sudo iptables-save | sudo tee /etc/sysconfig/iptables`)

8. Repeated steps 3–7 on every other app host in scope.

## What I Took Away From This

- Rule *order* in iptables is not cosmetic — with `-I` inserting at the top and `-A`
  appending at the end, getting the ACCEPT-before-REJECT order wrong would lock out the LBR
  too, since the REJECT would match first
- "Block for everyone except X" is really two rules, not one: an explicit allow for the
  exception, then a catch-all reject — order between them is what makes the exception
  actually work
- Saving the rules is a separate, easy-to-forget step — without it, everything resets on
  the next reboot and the port opens back up
- This was the first task that had to be repeated identically across multiple servers,
  which made me appreciate why config management tools (like the Ansible setup from Day 8)
  exist — doing this by hand across many hosts doesn't scale well

## Notes to Self

| iptables Concept | Detail |
|---|---|
| Tables | filter (default), nat, mangle, raw |
| Chains | INPUT (incoming), OUTPUT (outgoing), FORWARD (routing) |
| Targets | ACCEPT, REJECT, DROP, LOG |
| Rule processing | Top-to-bottom, first match wins |

| Flag | Purpose |
|---|---|
| `-A` | Append rule to the end of the chain |
| `-I` | Insert rule (default: at the top) |
| `-D` | Delete a rule |
| `-L -n -v --line-numbers` | List rules with numbering, useful for checking order |

| Persistence | Command |
|---|---|
| Save current rules | `service iptables save` |
| Alternative save | `iptables-save > /etc/sysconfig/iptables` |
| Restore rules | `iptables-restore < rules.txt` |
