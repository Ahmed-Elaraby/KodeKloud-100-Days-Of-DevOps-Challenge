# Day 009: Debugging MariaDB Issues

## 🎯 What I Did Today
Today's task was a real troubleshooting scenario —
an application couldn't connect to its database because the MariaDB service was down,
and I had to actually dig in and find out why instead of just restarting it and hoping.

**The scenario**: production support flagged that the app can't reach the database. Turned
out MariaDB was down on the DB server — need to find the root cause and bring it back up.

## Steps I Followed

1. Logged into the database server.

2. Checked the MariaDB logs first, since a blind restart without knowing *why* it went down
   isn't real troubleshooting:

    ```sh
    tail -f /var/log/mariadb.log
    ```

   The log just showed a normal shutdown sequence — no crash, no obvious error, which meant
   the "why" was somewhere else.

3. Checked the actual service status:

    ```sh
    sudo systemctl status mariadb
    ```

   Confirmed it: `inactive (dead)`, "MariaDB server is down".

4. Tried the straightforward fix first:

    ```sh
    sudo systemctl enable mariadb
    sudo systemctl start mariadb
    ```

   Still failed — meaning the problem wasn't "someone forgot to start it", something was
   actually preventing it from starting.

5. That pushed me to check the config, since the logs and a failed start with no errors
   often point to a config/path mismatch rather than a code or permissions problem:

    ```sh
    cat /etc/my.cnf.d/mariadb.service
    ```

   Found the issue: the config pointed `datadir` to `/var/lib/mysql/`, but the actual data
   was sitting in `/var/lib/mysqld`. A simple typo/mismatch was the entire root cause.

6. Fixed the config to point at the correct data directory, then restarted:

    ```sh
    systemctl restart mariadb
    ```

## What I Took Away From This

- Always check the logs before touching anything — a blind restart can hide the actual
  root cause instead of fixing it
- "Service won't start, no obvious log error" is a strong signal to check config file paths
  before anything else, especially data directory and socket paths
- A single wrong path in a config file can take a whole service down with a misleadingly
  clean shutdown log — the log itself won't always scream "this is wrong"
- Real troubleshooting is a process: check status → check logs → try the obvious fix →
  check config → fix the actual cause. Skipping steps just means you get lucky or you don't

## Notes to Self

| Area | Location |
|---|---|
| MariaDB log | `/var/log/mariadb/mariadb.log` (or `/var/log/mysqld.log`) |
| Main config | `/etc/my.cnf`, `/etc/my.cnf.d/` |
| Data directory (default) | `/var/lib/mysql/` |
| Socket file | `/var/lib/mysql/mysql.sock` |

| Command | Purpose |
|---|---|
| `systemctl status mariadb` | Check current service status |
| `journalctl -u mariadb` | View systemd logs for the service |
| `mysqladmin ping` | Quick connectivity test |
| `mysql -u root -p` | Connect directly to the database |

| Path | Expected Ownership | Expected Permissions |
|---|---|---|
| Data directory | `mysql:mysql` | `755` |
| Config files | `root:root` | `644` |
| Socket file | `mysql:mysql` | — |
| Log files | `mysql:mysql` | writable |
