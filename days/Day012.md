# Day 012: Linux Network Services

## 🎯 What I Did Today

Day 12 of my #100DaysOfDevOps challenge. Today's task was another real troubleshooting
scenario — Apache wasn't reachable on its configured port, and the cause could've been the
service itself, a port conflict, or the firewall. Had to actually investigate instead of
guessing.

**The scenario**: Apache on App Server 1 isn't reachable on port `6400`. Find and fix the
issue using tools like `telnet` and `netstat`, and make sure it's reachable from the jump
host without weakening any security settings. Also had to be careful not to touch
`index.html` — that alone would fail the task.

## Steps I Followed

There were actually **two separate problems** stacked on top of each other here — fixing
one wasn't enough on its own.

### Problem 1: Apache wasn't running at all

1. Checked the service status first:

    ```sh
    sudo systemctl status httpd
    ```

   Confirmed Apache was down.

2. Instead of just restarting blindly, checked *why* — looked at what was actually
   listening on port `6400`:

    ```sh
    sudo netstat -tlnup
    ```

   Found another process already holding port `6400`, which is exactly why Apache couldn't
   bind to it and start.

3. Killed the conflicting process so the port would be free, then started Apache:

    ```sh
    sudo kill <pid>
    sudo systemctl start httpd
    sudo systemctl status httpd
    ```

   Apache came up clean once the port was actually free.

### Problem 2: Still unreachable from the jump host

4. Apache was running locally, but `curl http://stapp01:6400` from the jump host still
   failed. That pointed away from the application and toward the network/firewall layer.

5. Checked the firewall rules on the app server:

    ```sh
    sudo iptables -L -n --line-numbers
    ```

   Found there was no rule allowing traffic in on port `6400` — new ports aren't open by
   default, so this made sense once I looked.

6. Added a rule to explicitly allow that port, without touching or loosening anything else
   already in place:

    ```sh
    sudo iptables -I INPUT -p tcp --dport 6400 -j ACCEPT
    ```

7. Tested from the jump host:

    ```sh
    curl http://stapp01:6400
    ```

   Worked once both issues were resolved.

## What I Took Away From This

- "Service is down" can have more than one layer to it — here it was port conflict *and*
  firewall, not just one or the other. Fixing the first problem doesn't mean the task is
  done
- A service failing to start because a port is already taken is a very different fix than a
  service that starts fine but isn't reachable — the symptoms look similar from the outside
  but need completely different tools to diagnose (`netstat` for the first, `iptables` for
  the second)
- Adding a firewall rule with `-I INPUT` inserts it without removing or disabling any
  existing rules — important when the task specifically says not to weaken security
  elsewhere
- Not touching `index.html` was a good reminder that "fix the problem" doesn't mean "change
  whatever's easiest" — the actual cause was infrastructure, not the app content

## Notes to Self

| Tool | Purpose |
|---|---|
| `netstat -tlnup` | See what's listening on which ports |
| `ss -tlnup` | Modern replacement for netstat |
| `telnet host port` | Test raw TCP connectivity to a port |
| `lsof -i :port` | Find which process owns a specific port |
| `iptables -L -n --line-numbers` | List firewall rules with numbering |

| Situation | Likely Cause | Where to Look |
|---|---|---|
| Service won't start | Port already in use | `netstat`/`lsof`, then kill the conflicting process |
| Service running, unreachable remotely | Firewall blocking the port | `iptables -L -n` |
