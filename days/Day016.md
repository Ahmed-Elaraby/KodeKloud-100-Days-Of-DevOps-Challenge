## Understanding the `http` Context First

`nginx.conf` is split into sections (contexts) — `events { }` handles connection-level
settings, and `http { }` handles anything web-related, including proxying and load
balancing. The task specifically required the load-balancing config to live inside `http {
}`, not anywhere else — so I made sure not to scatter config across separate files.

## Steps I Followed

1. Connected to the LBR server.

2. Installed Nginx (only if it wasn't already there):

    ```sh
    sudo yum install nginx -y
    ```

3. Edited the main config file:

    ```sh
    sudo vi /etc/nginx/nginx.conf
    ```

4. Added an `upstream` block listing all three app servers on their **existing** Apache
   port (left untouched, exactly as required), and a `server` block to proxy incoming
   requests to that pool — both inside `http { }`:

    ```nginx
    upstream backend_servers {
        server stapp01:<apache_port>;
        server stapp02:<apache_port>;
        server stapp03:<apache_port>;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://backend_servers;
        }
    }
    ```

    - `upstream backend_servers { }` — the pool of servers traffic gets distributed across
    - `proxy_pass http://backend_servers;` — forwards anything hitting the LBR to one of
      the servers in that pool

5. Validated the config before touching the running service:

    ```sh
    sudo nginx -t
    ```

6. Started/restarted and enabled Nginx:

    ```sh
    sudo systemctl restart nginx
    sudo systemctl enable nginx
    ```

7. Confirmed Apache was actually running on all three app servers (part of the
   requirement, not optional):

    ```sh
    sudo systemctl status httpd
    ```

8. Tested from the LBR:

    ```sh
    curl http://stlb01:80
    ```

## How I Actually Verified Load Balancing Was Working

Getting a `200` back once doesn't prove requests are being distributed — it only proves one
server responded. To actually see the distribution happening, I set each app server's
`index.html` to say which server it was, temporarily:

```sh
echo "Response from App Server 1" | sudo tee /var/www/html/index.html
# same idea on App Server 2 and 3, with their own labels
```

Then hit the LBR repeatedly:

```sh
curl http://stlb01:80
curl http://stlb01:80
curl http://stlb01:80
```

Watching the response change (or cycle) across requests confirmed the traffic was actually
going to different servers, not just being served by one the whole time. Nginx's default
algorithm is round robin, so three requests in a row should hit each server once, in order
— not randomly.

I also checked the access logs on each app server directly (`tail -f
/var/log/httpd/access_log`) while sending several requests from the LBR, and saw the hits
split across all three logs, which confirmed the same thing from the server side instead of
just the client side.

## What I Took Away From This

- A single successful `curl` doesn't prove load balancing is happening — it only proves the
  LBR can reach *a* backend. Real verification means seeing traffic split across servers
- Nginx defaults to round robin, not random distribution — that's useful to know when
  interpreting test results, since a predictable pattern (1, 2, 3, 1, 2, 3...) is actually
  the expected healthy behavior, not a bug
- Keeping the Apache port untouched on the app servers and only adding the proxy layer on
  top is the whole point of a load balancer — it shouldn't require changing anything on the
  backend servers themselves
- This task tied together almost everything from earlier days: Apache running correctly
  (Days 12/14), the right port configured (Day 11/12), and now a proxy layer sitting in
  front of all of it

## Notes to Self

| Concept | Detail |
|---|---|
| `upstream` block | Defines the pool of backend servers |
| `proxy_pass` | Forwards incoming requests to the upstream pool |
| Default algorithm | Round robin — cycles through servers in order |
| Other algorithms | `least_conn`, `ip_hash`, `random` |

| Verification Method | What It Shows |
|---|---|
| Changing each server's response content, then repeated `curl` | Confirms responses cycle across servers (client-side proof) |
| `tail -f access_log` on each app server while sending requests | Confirms each server actually received hits (server-side proof) |
| Custom `log_format` with `$upstream_addr` on the LBR | Shows exactly which backend handled each request, straight from Nginx's own log |
