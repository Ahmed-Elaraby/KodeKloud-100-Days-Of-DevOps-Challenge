# Day 014: Linux Process Troubleshooting

## 🎯 What I Did Today

Today's task was checking Apache across multiple app servers — 
and it turned out each server had a *different* problem, so the same
"restart and hope" approach wasn't going to work for all three.

**The scenario**: monitoring flagged Apache as unavailable on one of the app hosts.
Requirement: make sure Apache is up and running on all app hosts (no need to worry about
actual content/pages), and running specifically on port `6200` everywhere. Nothing said
the fix would be the same on every server.


## Steps I Followed

Checked all three servers one by one instead of assuming the issue (or the fix) would be
identical across them:

```sh
ssh tony@stapp01
sudo systemctl status httpd
```

...repeated the same check on App Server 2 and App Server 3.

### App Server 1 — port conflict

Apache wasn't running. Checked what was actually listening on port `6200`:

```sh
sudo netstat -tlnup
```

Found another process (sendmail, same pattern as [Day 12](./day-012-linux-network-services.md))
already holding the port, which is why Apache couldn't bind and start. Freed the port and
started Apache:

```sh
sudo kill <pid>
sudo systemctl start httpd
```

### App Server 2 — just needed a start

Apache was simply stopped here — no conflict, no bad config. A plain start fixed it:

```sh
sudo systemctl start httpd
```

### App Server 3 — wrong port configured

Apache was running, but not on the right port. Checked the config directly:

```sh
sudo grep -ri "listen" /etc/httpd/conf/httpd.conf
```

Found it was listening on a different port than required. Fixed the `Listen` directive
(and double-checked any `VirtualHost` block matched too):

```sh
sudo nano /etc/httpd/conf/httpd.conf
```

Set it to:

```
Listen 6200
```

Then restarted for the config change to apply:

```sh
sudo systemctl restart httpd
```

### Final check, all three servers

```sh
sudo systemctl status httpd
sudo netstat -tulnp | grep httpd
```

Confirmed all three showed `active (running)` and listening on `6200`.

## What I Took Away From This

- "Same symptom, same fix" is a trap — all three servers reported the same monitoring
  alert (Apache unavailable), but the actual causes were completely different: a port
  conflict, a simple stopped service, and a misconfigured port
- Checking the actual config (`Listen` directive) instead of just restarting is what caught
  App Server 3's issue — a restart alone would have "fixed" the service status while still
  leaving it on the wrong port
- Recognizing a pattern from an earlier day (the port conflict looked identical to Day 12)
  sped things up, but I still had to verify it rather than assume every server had the same
  root cause
- Working through multiple servers systematically — check, diagnose, fix, verify, next
  server — beats jumping straight to fixes based on what worked on the first one

## Notes to Self

| Symptom | Likely Cause | How I Found It |
|---|---|---|
| Service fails to start, "Address already in use" | Port conflict | `netstat -tlnup` |
| Service simply inactive, no errors | Just stopped | `systemctl status` |
| Service running but unreachable on expected port | Wrong port in config | `grep -ri "listen"` in the config file |

| Command | Purpose |
|---|---|
| `systemctl status httpd` | Check current service state |
| `journalctl -xe -u httpd --no-pager` | Deeper logs when status alone isn't enough |
| `apachectl configtest` / `httpd -t` | Validate config syntax before restarting |
| `netstat -tulnp \| grep httpd` | Confirm what Apache is actually listening on |
